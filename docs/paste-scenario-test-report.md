# 终端图片粘贴场景实测报告（v4.1）

本报告记录对 v4.1（PR #7 合并后）粘贴链路的系统性实测，分两轮：

- **第一轮（文件读取层模拟）**：把工具会注入终端的各类路径文本原样喂给 CLI Agent 的文件读取管线，验证"路径字符串 → 文件系统解析 → 图片渲染"。
- **第二轮（真实终端实测）**：在**真实的交互式 Claude Code TUI（v2.1.220）和 Kimi Code CLI（v0.29.1）**中，用 bracketed paste（与 Windows Terminal 收到 Ctrl+V 后发给 TUI 的字节序列一致）逐一粘贴各形态文本，直接观察输入框是否渲染 `[Image #n]` / 文件引用。

两轮均在 Linux 容器内完成，`/mnt/c/Users/<用户名>/wsl_clipboard/temp/clip_YYYYMMDD_HHMMSS_mmm.png` 目录与命名 1:1 模拟 WSL 真实输出。**尚未覆盖**：Windows 真机上 exe 本体的链路（全局热键捕获、剪贴板图片转 PNG、SendInput 注入、输入法保护、托盘），以及 Kimi 登录后 `@` 引用的提交时消费——见文末"待真机验证清单"。

## 结论

1. **v4.1 主链路在真实 Claude Code TUI 中完全正常**：先落盘 + plain 粘贴，含空格/中文路径、4K、6.2 MB 大图均瞬时转为 `[Image #n]`，无需任何引号或转义。
2. **issue #4 成因实证**：文件不存在（T5）或为空（T6）时不转换、路径留在输入框，与 FAQ Q1 一致；v4.1 的"先落盘再粘贴"从根上消除了该窗口。残余风险仅剩"文件头完好的半文件"（T7）：会转换成附件但提交后被拒收，且 `ensure_saved` 的 `try_exists` 短路会让这种残留文件永远不被重写修复。
3. **issue #5 实证**：Kimi Code CLI 确实不识别纯路径（K1），托盘切 `@` 风格是正确方向；`@` 引用的提交时消费需在登录后的真机确认（K2）。
4. **新发现——多文件连接方式决定能否转附件（T13/T14/T15）**：Claude Code 中换行连接的多路径**全部不转**，空格连接**全部转换**，引号+空格连接不转。当前 `PathStyle::Plain.format_paths` 用 `\n` 连接，意味着 **CF_HDROP 多张图片以 plain 风格粘进 Claude Code 时一张附件都不会生成**。
5. **`cargo check`/`clippy` 在 Linux 宿主验证通过，但有未写明的前提**：`rust/.cargo/config.toml` 强制 `x86_64-pc-windows-msvc`，需先 `rustup target add x86_64-pc-windows-msvc`（否则 `E0463`）。装好后 check 19.5s 通过，clippy 通过（8 个风格 warning）。README 编译章节已随本报告补充说明。

## 改进建议（本次仅记录，未改代码）

- **多文件 plain 连接符**（对应结论 4）：对 Claude Code，`Plain.format_paths` 可考虑在"所有路径均不含空格"时改用空格连接（全部转附件），含空格时回退换行；或新增托盘选项。需权衡：空格连接对 shell 场景不友好，且路径含空格时存在分词歧义。
- **半文件自愈**（对应结论 2）：`ensure_saved` 改为"写临时文件 + rename"原子落盘，并在 `try_exists` 命中时校验文件非空。
- README FAQ 可补充：Claude Code 下 plain 风格即可（`@` 风格粘贴不转附件）；多图请分次粘贴（当前版本换行连接不转附件）。
